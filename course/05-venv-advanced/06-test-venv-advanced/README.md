## Вопрос 1

Вы хотите создать venv на базе Python 3.11. Уже выполнили `pyenv local 3.11.7`. Какой порядок действий правильный?

- A) Сразу `python -m venv venv` — pyenv local уже активен
- B) Сначала `pyenv rehash`, затем `python -m venv venv`
- C) Вызвать `~/.pyenv/versions/3.11.7/bin/python -m venv venv` явно
- D) Сначала `source ~/.pyenv/version`, затем создать venv

<details><summary>Ответ</summary>

**A)** — `pyenv local 3.11.7` привязывает версию к текущей директории. Команда `python` теперь указывает на эту версию через shims pyenv. Можно сразу создавать venv.

**C)** тоже корректно — явный путь обходит любые настройки shell, но обычно достаточно A.

</details>

## Вопрос 2

Какой вывод вы ожидаете после `pip freeze > requirements.txt` в активированном venv, где установлены только `requests` и `rich`?

- A) Две строки: `requests` и `rich`
- B) Много строк — requests, rich и все их зависимости
- C) Пустой файл, если пакеты установлены в системный Python
- D) Ошибка, если venv не активирован

<details><summary>Ответ</summary>

**B)** — `pip freeze` выводит все установленные пакеты в формате `package==version`, включая транзитивные зависимости. Если venv активирован и пакеты стоят в нём, requirements.txt будет содержать полный список.

</details>

## Вопрос 3

Зачем нужен файл `.python-version` рядом с `requirements.txt` при передаче проекта коллеге?

- A) Он не нужен — достаточно requirements.txt
- B) pip читает его при `pip install -r requirements.txt`
- C) pyenv использует его для выбора версии Python; без него коллега может использовать другую версию
- D) Он нужен только для Jupyter

<details><summary>Ответ</summary>

**C)** — `.python-version` сообщает pyenv (и человеку), какую версию Python использовать для проекта. Без него коллега может установить пакеты через pip в venv от другой версии Python, что иногда вызывает несовместимости. Полное воспроизведение = версия Python + набор пакетов.

</details>

## Вопрос 4

Когда оправдано несколько venv в одной директории проекта?

- A) Никогда — один проект = одно окружение
- B) Когда нужны dev- и prod-окружения с разными версиями пакетов
- C) Когда тестируете совместимость кода с разными версиями Python
- D) Только B и C

<details><summary>Ответ</summary>

**D)** — Несколько venv в одном проекте оправданы, когда: (B) есть разделение dev/prod с разными зависимостями; (C) проверяете код на Python 3.11 и 3.12. Один проект = одно окружение — упрощение; в реальности могут быть исключения.

</details>

## Вопрос 5

Что делает флаг `--system-site-packages` при создании venv?

- A) Устанавливает системные пакеты в venv
- B) Даёт venv доступ к пакетам, установленным в базовый Python (site-packages)
- C) Копирует системный Python в venv
- D) Ничего — этот флаг устарел

<details><summary>Ответ</summary>

**B)** — venv, созданный с `--system-site-packages`, видит пакеты из site-packages базового Python. Пакеты не копируются, окружение просто имеет к ним доступ. По умолчанию venv изолирован и не видит системные пакеты.

</details>

## Вопрос 6

Как правильно удалить виртуальное окружение `venv`?

- A) `pip uninstall venv`
- B) `deactivate` и затем `rm -rf venv/`
- C) `python -m venv --remove venv`
- D) Только `rm -rf venv/` — деактивация не обязательна

<details><summary>Ответ</summary>

**B)** — venv — это просто директория. Удаление = `rm -rf venv/`. Деактивация перед удалением желательна: иначе в prompt останется префикс несуществующего пути, и команды могут вести себя непредсказуемо. Специальной команды деинсталляции нет.

</details>

## Вопрос 7

В активированном venv вы выполнили `pip install requests`. Где окажется пакет, если venv создан без `--system-site-packages`?

- A) В системном site-packages
- B) В `venv/lib/python3.x/site-packages/`
- C) В `~/.local/lib/`
- D) Зависит от настроек pip

<details><summary>Ответ</summary>

**B)** — В активированном venv команда `pip` связана с интерпретатором внутри venv. Пакеты устанавливаются в `venv/lib/python3.x/site-packages/`. Системный Python не затрагивается.

</details>

## Вопрос 8

Как проверить, что `pip` в текущей сессии указывает на venv, а не на системный Python?

- A) `echo $PATH` — первый путь должен содержать `venv`
- B) `which pip` — путь должен быть внутри директории venv
- C) `pip --version` — в выводе будет путь к Python внутри venv
- D) B и C

<details><summary>Ответ</summary>

**D)** — `which pip` покажет путь к исполняемому файлу; в активированном venv это путь вида `.../venv/bin/pip`. `pip --version` выводит путь к Python, с которым связан pip — он тоже должен быть внутри venv.

</details>

## Вопрос 9

В проекте есть `venv-py311` и `venv-py312`. Вы активировали `venv-py311`, установили пакет. Потом активировали `venv-py312`. Будет ли пакет доступен?

- A) Да — пакеты общие для всех venv проекта
- B) Нет — каждое окружение изолировано
- C) Только если пакет есть в requirements.txt
- D) Зависит от имени пакета

<details><summary>Ответ</summary>

**B)** — Каждое venv изолировано. Пакет, установленный в `venv-py311`, недоступен в `venv-py312`. Чтобы использовать пакет в другом окружении, нужно установить его там отдельно (например, через `pip install -r requirements.txt`).

</details>

## Вопрос 10

Коллега прислал проект с `requirements.txt` и `.python-version`. Какая последовательность команд воспроизведёт окружение?

- A) `pip install -r requirements.txt` — версия Python не важна
- B) `cd проект` → `pyenv install` (если версии нет) → `python -m venv venv` → `source venv/bin/activate` → `pip install -r requirements.txt`
- C) `python -m venv venv` → `pip install -r requirements.txt` — pyenv подхватит версию автоматически
- D) Только `pip install -r requirements.txt` в корне проекта

<details><summary>Ответ</summary>

**B)** — 1) Зайти в директорию проекта — pyenv прочитает `.python-version`. 2) При необходимости установить версию `pyenv install`. 3) Создать venv — он будет от нужной версии. 4) Активировать venv. 5) Установить пакеты из requirements.txt.

</details>
