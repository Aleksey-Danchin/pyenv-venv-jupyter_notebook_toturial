# pip vs системный пакетный менеджер (apt)

> **Модуль 3 · Урок 7** | Время: ~15 мин

## Почему pip ≠ apt

В Linux (Ubuntu, Kubuntu) пакеты устанавливаются через **apt** — системный пакетный менеджер. Он ставит софт в `/usr/`, управляет зависимостями между системными компонентами и обновлениями безопасности.

pip — менеджер пакетов **Python**. Он загружает библиотеки из PyPI и устанавливает их в `site-packages` конкретного интерпретатора Python.

Это **разные экосистемы**:

| Критерий | apt | pip |
|----------|-----|-----|
| Что устанавливает | Системные пакеты, в т.ч. `python3-*` | Python-библиотеки из PyPI |
| Куда ставит | `/usr/lib/python3.x/`, `/usr/bin/` | site-packages Python (системный или pyenv) |
| Обновления | `apt update && apt upgrade` | `pip install --upgrade <package>` |
| Цель | Системные инструменты, стабильность ОС | Разработка, проектные зависимости |

## Что ставит apt для Python

Пакеты вида `python3-*` — это Python-модули, упакованные для дистрибутива:

```bash
apt list --installed | grep python3
```

```
python3-pip/focal 20.0.2-5ubuntu1 amd64
python3-requests/focal 2.22.0-2ubuntu1 amd64
...
```

Они ставятся в системные пути и используются системными скриптами. Версии здесь «зашиты» в дистрибутив — часто старые.

## Риски смешивания pip и apt

Нельзя устанавливать **один и тот же пакет** и через apt, и через pip:

- apt поставит `python3-requests` в `/usr/lib/python3.x/dist-packages/`
- pip поставит `requests` в `site-packages` (которые идут раньше в `sys.path`)

Результат — путаница: какая версия активна, кто что обновил, почему `import` ведёт себя неожиданно.

**Правило:** для проектной разработки используйте **только pip** (лучше внутри venv). apt — только для системного Python и пакетов `python3-*`, которые явно нужны системе.

## Сравнение с альтернативами

### pip vs conda

Conda — менеджер пакетов и окружений, который управляет и Python, и библиотеками, и бинарными зависимостями. pip работает только с Python-пакетами.

| Аспект | pip | conda |
|--------|-----|------|
| Окружения | Нет (нужен venv) | Встроенные окружения |
| Бинарные зависимости | Зависит от сборки пакета | Conda их управляет |
| Репозиторий | PyPI | Anaconda / conda-forge |
| Интеграция с pyenv | Да | Обычно conda вместо pyenv |

В связке pyenv + venv + pip вы получаете контроль над версиями Python и изоляцией — без «тяжёлого» conda.

### pip vs pipx

**pipx** — инструмент для установки Python-приложений (CLI-утилит) в изолированные окружения. Каждое приложение получает свой venv.

- **pip** — ставит пакеты в текущее окружение (глобальное или venv).
- **pipx** — ставит CLI-утилиту (например, `black`, `poetry`) в отдельное изолированное окружение и создаёт симлинк в `~/.local/bin/`.

Для библиотек (import в коде) — pip. Для утилит, которые вызываются из терминала, — pipx удобнее, чем глобальный `pip install`.

## Частые ошибки

### Ошибка 1 — Устанавливать Python-библиотеки через apt

Пакеты `python3-requests`, `python3-numpy` в репозиториях часто устарели. Для разработки используйте `pip install` (в venv). apt — только если пакет нужен именно системным скриптам.

### Ошибка 2 — Обновлять pip-пакеты через apt

`apt upgrade` обновит только пакеты из apt. Пакеты, установленные через pip, apt не трогает. Обновление pip-пакетов — через `pip install --upgrade`.

### Ошибка 3 — Думать, что apt и pip «видят» друг друга

Они не синхронизированы. `apt list python3-*` и `pip list` показывают разные наборы. Путать их — путь к невоспроизводимым багам.

### Ошибка 4 — Удалять системный python3-pip

Пакет `python3-pip` даёт команду `pip3`. В связке с pyenv часто используется pip из `~/.pyenv/shims/pip`, но полностью удалять системный pip не стоит — некоторые системные инструменты могут от него зависеть.
