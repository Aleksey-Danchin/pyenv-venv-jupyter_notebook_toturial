# Что такое venv и зачем нужна изоляция

> **Модуль 4 · Урок 1** | Время: ~15 мин

## Проблема глобальной установки пакетов

В модуле 0 вы узнали, что pip по умолчанию устанавливает пакеты в **site-packages**[^глоссарий] — общую директорию для всего Python. Если вы используете pyenv (модули 1–2), пакеты идут в `~/.pyenv/versions/<version>/lib/.../site-packages/`. В любом случае это *одно* место на *одну* версию Python.

[^глоссарий]: [Глоссарий](../../references/glossary.md)

Что не так? Разные проекты требуют разных версий одних и тех же пакетов. Проект A нуждается в `requests==2.28.0`, проект B — в `requests==2.31.0`. Глобальная установка даёт только одну версию — последнюю. Либо вы переустанавливаете пакеты при переключении проекта, либо конфликтуют зависимости.

## Что такое venv

**venv** — встроенный в Python модуль для создания **виртуальных окружений**[^глоссарий]. Виртуальное окружение — это изолированная копия окружения выполнения Python: свой интерпретатор (или симлинк на него), отдельная директория site-packages, отдельный pip.

[^глоссарий]: [Глоссарий](../../references/glossary.md)

Каждый проект получает собственное окружение. Пакеты, установленные в окружении проекта A, не видны в проекте B. Это и есть **изоляция зависимостей**[^глоссарий].

[^глоссарий]: [Глоссарий](../../references/glossary.md)

## Зачем нужна изоляция

| Ситуация | Без изоляции | С venv |
|----------|--------------|--------|
| Два проекта с разными версиями одной библиотеки | Конфликт — последняя установка перезаписывает предыдущую | Каждый проект в своём окружении, версии не конфликтуют |
| Воспроизведение окружения коллеги | «У меня работает» — неизвестно, какие пакеты стоят глобально | `pip freeze` в venv даёт точный список зависимостей проекта |
| Зависимости системных утилит | `pip install` может сломать системные скрипты | Системный Python не трогается |
| Удаление проекта | Глобальные пакеты остаются, накапливается мусор | Удалить каталог venv — и всё чисто |

## venv и pyenv: разные задачи

В модуле 1 вы познакомились с **pyenv**[^глоссарий]. Важно не путать:

[^глоссарий]: [Глоссарий](../../references/glossary.md)

- **pyenv** — управляет *версиями интерпретатора* (Python 3.10, 3.12, 3.13).
- **venv** — управляет *изоляцией пакетов* внутри выбранной версии Python.

Они дополняют друг друга. Типичный рабочий поток: pyenv выбирает версию Python для проекта, venv создаёт изолированное окружение пакетов для этой версии. Подробнее — в модуле 5.

## Сравнение с альтернативами

### venv vs virtualenv

**virtualenv** — внешний пакет, появился раньше встроенного venv. venv встроен в Python с версии 3.3 (как модуль `venv` с 3.3, полноценная поддержка с 3.4).

| Критерий | venv | virtualenv |
|----------|------|------------|
| Установка | Встроен в Python | `pip install virtualenv` |
| Совместимость | Только Python 3.3+ | Python 2 и 3 |
| Команда создания | `python -m venv` | `virtualenv` |
| Поддержка | Стандартная библиотека | Community |

Для Python 3.4+ предпочтительно использовать встроенный venv — не требует установки, поддерживается разработчиками CPython.

## Частые ошибки

### Ошибка 1 — Путать venv с pyenv

venv и pyenv — разные инструменты. pyenv переключает версии Python; venv создаёт изолированные окружения для пакетов. Оба используются в работе: сначала pyenv (или системный Python), потом venv.

### Ошибка 2 — Использовать venv без понимания цели

venv нужен для изоляции зависимостей между проектами. Если у вас один проект и вы никогда не сталкивались с конфликтами версий — venv всё равно полезен: он упрощает воспроизведение окружения и не засоряет глобальный site-packages.

### Ошибка 3 — Думать, что venv заменяет pyenv

venv не устанавливает и не переключает версии Python. Он создаёт окружение на базе *уже выбранного* интерпретатора. Если нужен Python 3.10 для проекта — сначала pyenv (или системная установка), затем venv.
