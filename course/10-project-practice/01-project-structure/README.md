# Структура Python-проекта: что где лежит

> **Модуль 10 · Урок 1** | Время: ~15 мин

## Зачем нужна структура

Структура проекта — это организация файлов и папок, чтобы код, тесты, конфигурация и документация находились в предсказуемых местах. Единообразие помогает вам и коллегам быстро ориентироваться и воспроизводить окружение.

В модулях 2–5 и 6–9 вы освоили pyenv, venv, pip и Jupyter. Теперь важно собрать всё в целостный проект, который можно передать коллеге или опубликовать.

## Типовая структура Python-проекта

```
my_project/
├── .python-version          # Версия Python для pyenv
├── requirements.txt        # Production-зависимости
├── requirements-dev.txt    # Dev-зависимости (опционально)
├── README.md                # Описание проекта
├── src/                     # Исходный код приложения
│   └── my_project/
│       └── __init__.py
├── tests/                   # Тесты
│   └── test_something.py
├── docs/                    # Документация (опционально)
└── scripts/                 # Вспомогательные скрипты (опционально)
```

### Корневая директория

В корне проекта обычно лежат:

| Файл / папка | Назначение |
|--------------|------------|
| `.python-version` | Версия Python для pyenv[^глоссарий](../../references/glossary.md) — читается pyenv при входе в директорию |
| `requirements.txt` | Список зависимостей в формате `package==version` для воспроизведения окружения |
| `README.md` | Краткое описание проекта, как установить и запустить |
| `venv/` | Виртуальное окружение (не коммитится в git — об этом в следующем уроке) |

### Папка `src/`

Исходный код приложения размещают в `src/` или в папке с именем проекта. Это отделяет «рабочий» код от тестов, скриптов и конфигов.

```
src/
└── my_project/
    ├── __init__.py
    ├── main.py
    └── utils.py
```

Альтернатива — плоская структура с пакетом в корне: `my_project/`, `main.py` рядом. Для небольших проектов допустимо; для библиотек и приложений с подмодулями `src/` предпочтительнее.

### Папка `tests/`

Тесты хранят в отдельной директории `tests/`. Имена тестовых файлов обычно начинаются с `test_`, чтобы их находили pytest и другие фреймворки.

```
tests/
├── test_main.py
└── test_utils.py
```

### Опциональные папки

| Папка | Назначение |
|-------|------------|
| `docs/` | Документация: Sphinx, MkDocs, заметки |
| `scripts/` | Утилиты: сборка, миграции, одноразовые скрипты |
| `notebooks/` | Jupyter-ноутбуки (если проект использует их регулярно) |

## Связь с pyenv, venv и Jupyter

- **`.python-version`** — pyenv читает его при `cd` в проект; `python` и `pip` будут указывать на нужную версию.
- **venv** — создаётся в корне (`python -m venv venv`) или в подпапке; активируется через `source venv/bin/activate`.
- **requirements.txt** — создаётся `pip freeze`, воспроизводится `pip install -r requirements.txt`.
- **Jupyter** — ноутбуки в `notebooks/` или в корне; ядро — активированное venv, зарегистрированное через ipykernel.

## Минимальный скелет проекта

Для учебного или небольшого проекта достаточно:

```
project/
├── .python-version
├── requirements.txt
├── README.md
├── src/
│   └── __init__.py
└── venv/           # создаётся вручную, не коммитится
```

## Частые ошибки

### Ошибка 1 — Всё свалено в корень

Один `main.py` в корне — допустимо для простого скрипта. Для проекта с несколькими модулями лучше выделить `src/` или пакет. Иначе корень разрастается, тесты смешиваются с кодом, и навигация усложняется.

### Ошибка 2 — Нет `.python-version`

Без `.python-version` коллега не узнает, какую версию Python использовать. pyenv подхватит глобальную версию, что может не совпадать с той, на которой вы разрабатывали. Всегда фиксируйте версию Python для воспроизводимости.

### Ошибка 3 — Не различать production и dev-зависимости

Jupyter, pytest, black — инструменты разработки. Они не нужны в production. Смешивание всего в одном `requirements.txt` раздувает окружение и усложняет деплой. В следующем уроке — как разделить зависимости.
